# Repository Guidelines

## Project Overview

Familiar is a local-first desktop companion for coding agents. It collects
agent activity through supported hook APIs, normalizes events in Rust, and
renders status through a Tauri desktop application with a vanilla JavaScript
frontend.

Keep changes consistent with the privacy-first design: do not add telemetry or
send captured prompts, transcripts, file contents, or hook payloads to remote
services unless the user explicitly requests that behavior.

## Repository Layout

- `crates/familiar-core/`: shared configuration, events, state machine,
  statistics, storage, and plugin abstractions.
- `crates/familiar-hooks/`: Claude Code, Codex, and Antigravity hook parsing,
  injection, preview, and uninstall behavior.
- `crates/familiar-api/`: REST and WebSocket API routes.
- `crates/familiar-cli/`: lightweight hook-reporting CLI.
- `app/src-tauri/`: Tauri application composition, commands, tray integration,
  and platform-specific window behavior.
- `app/src/`: vanilla JavaScript, HTML, CSS, and canvas renderers.
- `config/default.toml`: versioned default configuration that the development
  app may also rewrite while saving settings.
- `sprites/`: source sprite packs and manifests.
- `docs/DESIGN.md`: architecture and protocol background.
- `docs/RELEASE_PROCESS.md`: versioning, validation, packaging, artifact
  archiving, tagging, and GitHub Release workflow.

Do not hand-edit files under `app/src-tauri/gen/schemas/`; they are generated by
Tauri. Do not commit build outputs or local state such as `target/`,
`app/node_modules/`, `app/dist/`, `.idea/`, `.DS_Store`, or log files.

## Working Agreements

- Inspect `git status` before editing and before committing. Preserve unrelated
  user changes and untracked files.
- Keep changes scoped to the request. Do not fix unrelated warnings, formatting
  debt, or failing tests unless they block the requested work.
- Prefer existing workspace dependencies and patterns. Ask before adding a new
  production dependency.
- Treat hook input and configuration files as untrusted external data. Avoid
  new panics on malformed input and return actionable errors.
- Do not modify user-level agent configuration such as `~/.claude`,
  `~/.codex`, or `~/.gemini` unless the user explicitly asks for it.
- When changing a serialized configuration field, update
  `config/default.toml`, preserve backward-compatible defaults where practical,
  and add a focused test.
- Before committing `config/default.toml`, verify that its diff is intentional;
  opening the settings UI can rewrite local values.

## Build and Development Commands

Run Rust commands from the repository root:

```bash
cargo check --workspace
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
```

Start with the narrowest relevant package or test while iterating, for example:

```bash
cargo check -p familiar-core
cargo test -p familiar-core --test config
cargo clippy -p familiar-core --lib -- -D warnings
```

The repository currently contains unrelated Rust formatting differences.
Format only Rust files touched by the task:

```bash
rustfmt path/to/changed.rs
rustfmt --check path/to/changed.rs
```

For the frontend and desktop application:

```bash
cd app
npm ci
npm run build
npm run tauri dev
```

`npm run build` is the available automated frontend validation. There are
currently no frontend lint or test scripts. Use `npm run tauri dev` only when
interactive desktop verification is relevant.

If a broad check fails for a pre-existing reason, run the focused checks that
cover the change and report the unrelated failure clearly.

## Code Conventions

- Use Rust 2021 idioms and keep crate responsibilities separated.
- Put shared domain behavior in `familiar-core`, vendor-specific integrations in
  `familiar-hooks`, transport behavior in `familiar-api`, and desktop wiring in
  `app/src-tauri`.
- Keep macOS-only APIs behind `#[cfg(target_os = "macos")]` and retain
  non-macOS behavior.
- Keep the frontend framework-free unless the user explicitly requests an
  architectural change. Use ES modules and the existing renderer abstractions.
- Use the global toast as the standard notification channel for transient
  status in the settings panel: `showToast(message, type, durationMs)` in
  `app/src/settings.js`, styled as `.app-toast` (fixed bottom-center, auto-
  dismiss). Surface one-shot feedback there — auto-save progress
  ("Saving..."/"Auto-saved"/"Save failed"), hook test results, copy
  confirmations — instead of adding new inline status labels or corner
  indicators, which truncate and break the unified design language. Reserve
  inline text for persistent state only. Toast types: `success` (green) and
  `error` (red); omit the type for neutral progress messages.
- Update both Chinese and English entries in `app/src/i18n.js` when adding or
  changing user-facing text.
- Within each settings-panel group, order controls by user intent: visibility
  toggles first, visual-style selectors second, display-detail controls (such
  as position, layout, alignment, opacity, and behavior) next, and size or
  scale adjustments last. Omit categories that do not apply, while preserving
  this relative order.
- Prefer focused comments that explain platform constraints or non-obvious
  behavior; do not narrate straightforward code.

## Verification

- Add or update tests for changed Rust behavior.
- For hook changes, cover parsing, injection, preview, and uninstall behavior
  as applicable.
- For configuration changes, verify both deserialization of older files and the
  serialized TOML output.
- For frontend changes, run `npm run build` and manually exercise the affected
  Tauri window when feasible.
- Check `git diff --check` before handing off.

Do not claim that a broad command passed if only a focused check ran. Include
the exact failing command and cause when verification is incomplete.

## Git and Review

- Follow the existing Conventional Commit style, such as `feat:`, `fix:`,
  `chore:`, or a scoped form like `fix(config):`.
- Stage only files that belong to the requested change.
- Do not rewrite history, force-push, create releases, or publish artifacts
  unless the user explicitly requests it.
- Summaries should state the behavior changed, the checks run, and any known
  limitations or pre-existing failures.

For a release, follow [`docs/RELEASE_PROCESS.md`](docs/RELEASE_PROCESS.md).
Keep local release binaries under the ignored `release-artifacts/<version>/`
directory, and never move or overwrite a tag that has already been pushed.
